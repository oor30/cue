# Cue 開発指示書

## 1. 目的

macOS上でオンライン／オフライン会議をリアルタイムに解析し、ユーザーへ能動的な助言を提示する「Cue」を開発する。

単なる議事録AIではなく、会議中にユーザーが「今、何を聞くべきか」「どう回答すべきか」「どこに矛盾・リスクがあるか」「要望に対してどんな仕様案が考えられるか」を即座に判断できる、**リアルタイム業務支援AI**を目指す。

初期利用者はシステムエンジニア1名を想定するが、将来的には社内配布・製品化を見据えた拡張可能な設計とする。

---

# 2. 基本コンセプト

## 2.1 主要ユースケース

主な利用シーンは以下。

* Zoomを利用した顧客とのオンライン打ち合わせ
* Zoomを使用しない社内会議
* Macからテレビ・外部ディスプレイへ資料を映して進行する会議
* システム開発案件の要件定義・仕様確認・顧客ヒアリング
* 将来的には営業・PM・その他職種での利用

Zoom APIには依存せず、macOS側で画面・音声を取得する。

これによりZoom以外の会議にも対応可能とする。

---

# 3. 技術方針

## 3.1 アプリケーション

macOSネイティブアプリとして実装する。

第一候補：

* Swift
* SwiftUI
* ScreenCaptureKit
* AVFoundation等のmacOS標準API

Electron等は原則採用せず、OS連携・画面キャプチャ・音声取得・フローティングUI・メニューバー・グローバルショートカットを安定して実装できるmacOSネイティブ構成を優先する。

ただし技術的に明確なメリットがある場合は、一部WebView等を利用してもよい。

---

# 4. AIエンジン

## 4.1 基本思想

Cue独自のAI環境を新たに構築するのではなく、ユーザーが既に利用しているAI開発環境を活用する。

初期対応：

* Codex
* Claude Code

将来的に拡張可能：

* OpenAI API
* Anthropic API
* その他ローカル／クラウドLLM

## 4.2 Codex

Codexを最優先で対応する。

対象プロジェクトのディレクトリをworking directoryとしてCodexを実行し、既存の環境を可能な限りそのまま利用する。

例：

* AGENTS.md
* Codex設定
* MCP
* Gitリポジトリ
* プロジェクト内ドキュメント
* ソースコード
* その他Codexからアクセス可能なツール

Cue側でこれらを二重管理しない。

## 4.3 Claude Code

Claude Codeを選択した場合も同様。

対象プロジェクトディレクトリを基準として、

* CLAUDE.md
* MCP
* Claude Code設定
* プロジェクトファイル

等を既存環境から利用する。

## 4.4 AIエンジン抽象化

以下のようなProvider層を設ける。

```text
AIProvider
├── CodexProvider
├── ClaudeCodeProvider
└── FutureProvider
```

UI・会議解析ロジックが特定AIへ強く依存しないようにする。

# 5. プロジェクト管理

## 5.1 基本方針

Cue内にプロジェクト登録機能を設ける。

ただし、資料や設定をCue用に再登録させるような多重管理は避ける。

基本的には既存のプロジェクトディレクトリを指定するだけとする。

例：

```text
プロジェクト名：
JAMD

Project Root：
/path/to/project

AI：
Codex

Web検索：
有効

Profile：
System Engineer
```

## 5.2 プロジェクト自動探索

指定されたProject Root配下をAI自身が必要に応じて探索する。

例：

```text
project/
├── AGENTS.md
├── CLAUDE.md
├── README.md
├── docs/
├── requirements/
├── meeting-notes/
├── circleback/
├── src/
└── ...
```

以下について個別登録を必須にしない。

* 要件定義書
* 仕様書
* Circleback議事録
* README
* Markdown
* ソースコード
* Git情報

AIが必要に応じて探索する。

## 5.3 追加参照先

必要な場合のみ、Project Root外の追加ディレクトリを登録可能とする。

例：

```text
~/Documents/MeetingNotes/JAMD/
```

設定項目：

* Additional Reference Paths
* Exclude Paths
* Priority Files
* Read/Write Policy

# 6. ファイルアクセス権限

## 6.1 ソースコード

原則Read-Only。

会議中のAIが、

* コード修正
* Git commit
* ファイル削除
* 自動リファクタリング

等を行わないようにする。

コード探索・grep・Git履歴確認等は許可する。

## 6.2 資料

資料ファイルは書き込み可能。

対象例：

* Markdown
* 議事録
* 要件定義書
* TODO
* Meeting Note
* 仕様資料

ただし、AIが会議中に無断で大量変更するのではなく、重要な変更については原則としてユーザー承認を介せる設計とする。

# 7. 画面取得

## 7.1 ScreenCaptureKit

macOSのScreenCaptureKitを使用する。

取得対象：

* Zoom
* ブラウザ
* VS Code等のIDE
* PDF
* Excel
* Slack
* メモ
* その他ユーザーが会議中に参照する画面

## 7.2 キャプチャ範囲

ユーザー設定で以下を選択可能にする。

* Zoomのみ
* 指定アプリ
* 指定ウインドウ
* ディスプレイ全体

デフォルトではZoom使用中はZoomを優先的に解析する。

ただし別アプリで資料・議事録・ソースコード等を開いた場合、それらもコンテキストとして利用可能とする。

## 7.3 画面保存

設定可能とする。

選択肢：

* 保存しない
* AIが重要と判断した画面のみ保存
* 定期スクリーンショット保存
* 可能であれば全映像保存

デフォルト：

**保存しない。解析後破棄。**

# 8. 音声取得

以下双方を取得する。

* Macから出力されるシステム音声
* ユーザー自身のマイク入力

つまり、

```text
相手の発言
+
自分の発言
```

双方をリアルタイム解析する。

---

# 9. 文字起こし

## 9.1 優先順位

日本語を最優先とする。

基本思想：

```text
リアルタイム処理に支障がない範囲で
精度を最大化
```

英語対応は必須ではない。

## 9.2 ストリーミング

音声を一定時間まとめてから処理するバッチ方式ではなく、可能な限りストリーミングに近い方式とする。

発言途中の暫定テキストと、確定テキストを区別して扱える設計が望ましい。

---

# 10. 話者識別

可能な限り複数話者を識別する。

理想：

```text
自分
クライアントA
クライアントB
社内担当者
```

ただし話者識別処理によってリアルタイム性が大きく低下する場合は、リアルタイム性を優先する。

最低限、

* 自分
* 自分以外

は識別する。

会議後に高精度な再解析を行い、話者情報を補完する方式も許容する。

---

# 11. 会議状態管理

アプリ内部で常時以下の情報を管理する。

例：

```text
MeetingState

- currentTopic
- transcript
- speakers
- decisions
- questions
- requirements
- unresolvedIssues
- actionItems
- risks
- previousSuggestions
- currentScreenContext
```

過去の全文字起こしを毎回AIに再送するような非効率な実装は避ける。

必要に応じて、

* 要約
* 構造化されたMeeting State
* 直近の発言
* 関連資料

を組み合わせてAIへ渡す。

---

# 12. イベント検知

## 12.1 基本思想

完全なポーリング式でもユーザー手動式でもなく、

**AI／アプリが自動でイベントを検知する。**

ユーザー操作は不要。

## 12.2 検知対象

最低限以下を検知する。

### 質問

例：

```text
できますか？
どうすればいいですか？
いつまでですか？
いくらかかりますか？
```

### 新規要望

例：

```text
〜できるようにしたい
〜を追加してほしい
```

### 仕様変更

既存仕様と異なる要求。

### 矛盾

以下との矛盾を検知する。

* 過去の会話
* プロジェクト資料
* ソースコード
* 過去議事録

### 決定事項

例：

```text
ではこの仕様で進めます。
```

### TODO／宿題

例：

```text
確認しておきます。
後で送ります。
```

### リスク

技術・納期・コスト・セキュリティ等。

### 重要情報

* 日付
* 金額
* 担当者
* 期限
* 契約条件

### 議論停滞

同じ論点について長時間決着していない場合。

---

# 13. ハイブリッドAI処理

常時重いAI推論を実行しない。

以下の二段構成とする。

```text
Realtime Monitor
↓
Event Detector
↓
必要な場合だけ
Deep AI Analysis
```

## 13.1 Realtime Monitor

常時、

* 発言
* Meeting State
* 画面変化

を監視する。

比較的軽量な処理とする。

## 13.2 Deep Analysis

重要イベント発生時のみ、

* Codex
* Claude Code

へ本格的な推論を依頼する。

必要に応じて、

* ソースコード検索
* 資料検索
* Git履歴確認
* Web検索

まで行う。

---

# 14. AIの主要役割

System Engineer Profileでは最低限以下を実装する。

## 14.1 質問すべき内容

例：

```text
💡 確認推奨

この要望では対象ユーザーの権限が不明です。

「管理者のみ利用可能ですか？」
を確認すると仕様を確定できます。
```

## 14.2 クライアント質問への回答候補

```text
💬 回答候補

既存仕様では〜となっています。

今回の要望は技術的には対応可能ですが、
○○について確認が必要です。
```

## 14.3 矛盾・誤り

```text
⚠️ 矛盾の可能性

現在の説明は既存仕様と一致しません。

根拠：
requirements.md
billing.php:182
```

## 14.4 仕様提案

原則複数案を出す。

例：

```text
🛠 仕様候補

A案
既存テーブル拡張

B案
履歴テーブル追加

C案
イベント方式

推奨：B案
```

## 14.5 リスク

* 技術リスク
* 工数増加
* データ移行
* セキュリティ
* 運用負荷

## 14.6 決定事項／TODO

会議中にも随時検出する。

# 15. AI出力カード

会議中の情報はカード形式で表示する。

カードカテゴリ例：

* 💬 回答
* 💡 質問
* ⚠️ 矛盾
* 🛠 仕様
* 🔍 調査
* 📌 決定
* ✅ TODO
* 🚨 リスク

## 15.1 表示内容

各カードには最低限、

```text
カテゴリ
タイトル
短い本文
重要度
確信度
根拠
生成時刻
```

を持たせる。

例：

```text
📌 重要
仕様上の矛盾

確信度 92%

現在の要望は既存の税込処理と
整合しない可能性があります。

・billing.php:182
・2025-08仕様書
```

---

# 16. 確信度

AIの提案には確信度を表示する。

例：

```text
95% 高
72% 中
41% 低
```

単純なモデル自己申告だけに依存せず、

* 根拠数
* ソース品質
* コード確認済み
* Web確認済み
* プロジェクト資料との一致度

等を可能な範囲で加味する。

---

# 17. 根拠表示

AIの重要な判断には根拠を必須とする。

例：

```text
根拠

requirements.md
billing.php:182
Circleback 2026-08-20
Anthropic公式
```

会議中は簡潔に表示。

クリックすると詳細を開ける。

ユーザー操作は不要。

例：

## 18.2 Deep Search

重要な質問の場合、

* 複数ソース

程度に表示する。

# 19. Fast / Deepモード

## Fast

会議中に即利用するための回答。

目標：

数秒以内。

表示は短くする。

## Deep

以下を必要に応じて実行する。

* ソース探索
* 資料探索
* Git履歴
* Web調査
* 複数案比較
* リスク評価

時間がかかることを許容する。

## 自動Deep

AI自身が、

```text
この質問は即答すると危険
```

と判断した場合、自動でDeep Analysisへ移行可能。

UIには、

```text
🔍 詳細調査中
```

などを表示する。

# 22. UI構成

## 22.1 メイン

推奨：

**右端サイドパネル + フローティング通知**

### サイドパネル

会議中のカードをタイムライン表示する。

### フローティング表示

重要なカードのみ一時表示する。

## 22.2 カードの寿命

カードはイベント発生時のみ作成する。

固定間隔で無意味にカードを生成しない。

高重要度のカードは自動ハイライト。

ユーザーまたはAIが重要と判断したカードは固定可能。

---

# 23. カード過多対策

以下の指標でカード表示を抑制する。

```text
Importance
×
Confidence
×
Novelty
```

似た内容のカードを短時間に何度も生成しない。

同一トピックのカードは更新・統合することも検討する。

# 33. セキュリティ

初期MVPでは過度なガードレール機能は不要。

ただし将来の顧客会議・社内配布を考慮し、設計上は以下を意識する。

* 保存データの場所を明確化
* AIへ送信するデータの可視化
* 削除機能
* プロジェクト単位のデータ分離
* APIキー等のSecretをログへ保存しない
* ソースコードRead-Only保証

---

# 34. ログ

開発・デバッグ用ログとユーザーデータを分離する。

以下を確認可能とする。

* AIリクエスト
* 処理時間
* イベント検知
* AI Provider
* エラー
* Web検索有無
* 参照資料

ただし機密情報を不要にログへ書かない。

---

# 35. パフォーマンス

最重要要件の一つ。

会議中に、

* 音声取得
* STT
* 画面解析
* AI推論
* Web検索
* ソース探索

を行うため、処理が会議時間に追いつかなくなることを絶対に避ける。

必要に応じて処理優先度を設ける。

例：

```text
Priority 1
音声・文字起こし

Priority 2
質問イベント

Priority 3
回答候補

Priority 4
画面解析

Priority 5
Deep Analysis
```

Deep処理が遅延してもリアルタイム文字起こしを止めない。

---

# 36. 非同期処理

各処理を可能な限り疎結合にする。

例：

```text
Capture
↓
Transcription
↓
Event Detection
↓
Suggestion Queue
↓
AI Provider
↓
UI
```

長時間のDeep Analysisによって他処理をブロックしない。

# 37. AI処理のキャンセル

話題が変わった場合などにDeep Analysisをキャンセルできる。

また、古くなった分析結果をそのまま表示しない。

結果生成時に、

```text
現在の会話トピックとまだ関連するか
```

を確認する。

# 39. UX上の最重要要件

このアプリによって会議への集中力を落としてはいけない。

ユーザーが会議中に読む情報量は極めて少なくする。

悪いUI：

```text
長文のAI回答が大量に流れる
```

良いUI：

```text
⚠️ 仕様矛盾 92%

既存の税込処理と一致しません。

[詳細]
```

つまり、

**一目で判断 → 必要なら詳細**

を徹底する。

# 40. プロダクトとしての差別化

Circleback等の議事録AIとは役割を明確に分ける。

主目的は、

```text
何が話されたか
```

ではなく、

```text
今この瞬間、
ユーザーは何を
聞く・言う・判断すべきか
```

を提示すること。

製品コンセプト：

**Real-time Cue**

特に初期段階では、

**Real-time System Engineer Copilot**

として完成度を高める。

# 41. 開発時の進め方

いきなり全実装を開始しないこと。

まず以下を行う。

1. 本指示書を分析
2. 技術的実現可能性を確認
3. macOSの現行APIを調査
4. Codex CLIとの安全な統合方法を確認
5. STT候補を比較
6. アーキテクチャ設計
7. MVP範囲を提案
8. ディレクトリ構成を提案
9. データモデルを提案
10. UI構成を提案
11. リスクを洗い出す

その結果をユーザーへ提示する。

重大な設計上の問題がないことを確認した後、実装へ進む。

# 42. Codexへの重要指示

このプロジェクトでは、単に「動くもの」を最短で生成することを目的としない。

以下を重視する。

* 保守性
* 拡張性
* リアルタイム性能
* macOS標準APIの適切な利用
* AI Providerの疎結合
* テスト可能性
* エラー処理
* 長時間会議での安定性
* メモリ使用量
* バックプレッシャー
* キュー管理
* AI応答遅延
* 音声処理遅延
* プライバシー
* 将来的な社内配布

特に、

**「1時間以上の会議を継続しても、処理遅延が積み上がってリアルタイム性を失わないこと」**

を非常に重要な非機能要件として扱う。
